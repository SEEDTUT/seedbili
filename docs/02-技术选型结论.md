# 技术选型结论：Kotlin + Compose Desktop

> 对应需求书第二章。结论先行，依据在后。
> 结论：**Kotlin/JVM + Compose Multiplatform for Desktop**。放弃 Flutter。
> 附带结论：同时排除 Tauri/Electron/Python+Qt（第五章「体积优先」与「不接触密码」两个约束下的比较）。

## 一、先说决定性的一条

选型不只是纸面比较，还要看**这台机器今天能不能产出安装包**。实测结果：

| 检查项 | 实测 | 对 Flutter 的影响 | 对 Kotlin 的影响 |
|---|---|---|---|
| `flutter` / `dart` | 未安装 | 需先装 SDK（≈1.5GB，含 Dart + Windows embedder 工具链） | 不需要 |
| Visual Studio 2022 / Build Tools | 未安装（`C:\Program Files\Microsoft Visual Studio\2022` 不存在） | **必需**：CMake + MSVC `cl.exe`/`link.exe`，「桌面开发 C++」负载 3–8GB | 不需要 |
| `cmake` | 未安装 | 必需 | 不需要 |
| Rust（`cargo 1.98.1`） | 已装，但只有 `x86_64-pc-windows-gnu` 工具链，没有 MSVC 链接器 | — | Tauri 也因此走不通（见第四节） |
| JDK | `jdk-17.0.2` + `jdk-25.0.4.1+1`，**都带 `jmods/`（70+ 个）** | — | jpackage 能直接产 app-image / msi / exe |
| Gradle | 8.11.1 已装，本地已缓存 8.14.3 / 9.1.0 / 9.5.1 / 9.8.0 发行包 | — | 可用 |
| Compose MP 依赖 | `org.jetbrains.compose.desktop:desktop-jvm:1.12.2`、`skiko-awt:0.150.2` 等**已在本地 Gradle 缓存** | — | 几乎零冷启动成本 |
| WiX 工具集 | `~/.gradle/compose-jb/wix311.zip` 已缓存 | Flutter 无内置打包器，安装包要自己造 | `packageMsi` 直接可用 |
| WSL | **未安装**（`wsl -l -v` 返回「未安装适用于 Linux 的 Windows 子系统」） | 两边都受影响 → 见需求书第三章，本项目把沙箱做成可插拔后端 | 同左 |
| 现存同类工程 | `D:\seed\KizunaToolbox`、`D:\seed\KizunaToolbox-New` 都是 Compose Desktop 工程 | — | 构建配方已被验证过，可直接复用 |

这一条就足以定结论：**Flutter 路线今天必须先装 3–8GB 的 Visual Studio 负载才能开始，而 Kotlin 路线今天就能出安装包。**需求书写了「体积优先」「不要反复打断」，为了一个还没验证过的 UI 框架去装半台机器的编译器，不划算。

## 二、按需求书要求的维度逐项比较

打分口径：5 好 / 3 中 / 1 差。「实测」列写的是本项目会真实碰到的东西，不是传闻。

| 维度 | Flutter (Dart + Windows embedder) | Kotlin + Compose Desktop | 胜方 |
|---|---|---|---|
| **Windows 桌面成熟度**（打包/安装包/DPI/托盘/自启） | 3。构建产物是裸目录（`exe` + `flutter_windows.dll` + `data/`），**官方不提供安装包工具**，MSI/EXE 要自己接 Inno Setup/NSIS/WiX。托盘、开机自启、通知全靠第三方插件（`tray_manager`、`win32_registry`），质量参差。DPI 支持 per-monitor v2，这块没问题。 | 5。Gradle 插件内置 `packageMsi`/`packageExe`（走 jpackage + WiX），一条命令出安装包，自带开始菜单项、桌面快捷方式、卸载器、`perUserInstall`（**不需要 UAC**）。DPI 由 AWT/Skia 处理。托盘用 AWT `SystemTray` 是 JDK 内建能力。 | **Kotlin** |
| **开发效率**（UI 迭代/热重载/布局表达力） | 5。hot reload 是真的快，布局表达力强，`Row/Column/Stack` + `Expanded` 心智负担低。 | 4。Compose 布局能力等价（`Row/Column/Box/Modifier`），1.12 也有 hot reload，但 JVM 全量编译的重编译循环比 Dart 慢一拍；大改状态结构时要重启进程。 | Flutter |
| **与本地进程集成**（子进程/stdin-stdout/进程管理/调虚拟 Linux 环境） | 3。`dart:io` 的 `Process.start` 可用，但要跟 Windows 控制台管道、GBK/UTF-8 混合编码、`wsl.exe` 输出（UTF-16LE，实测本项目环境就是这副样子）打交道时，Dart 侧的转码和进程树终止（杀掉 `wsl.exe` 不会带走里面的进程）都要手写 FFI 兜底。 | 5。`ProcessBuilder` + `redirectErrorStream` + `BufferedReader` 是母语级；`ProcessHandle.descendants()` 能整棵树杀干净（这一点对「一键清理不留垃圾」很关键）；JNA 直接调 DPAPI/`advapi32`/注册表。 | **Kotlin** |
| **与 Python 生态协同**（现有管线复用还是重写） | 2。手机端管线是 Python。Flutter 只能起子进程调 `python.exe`，意味着安装包还得捆一个 Python 运行时（≈40MB+，且 pip 依赖树在 Windows 上极难冻结），或者要求用户自己装 Python —— 对「用户只负责配置和管理」的产品定位是不可接受的。 | 2 → 4。同样不能进程内调 Python，但**结论是重写而不是复用**：管线的核心是三件事——抓评论、判一次、发一条，B 站接口是 HTTP + Cookie + WBI 签名，在 JVM 上重写约 600 行，换来零外部运行时。Kotlin 协程写并发抓取/限速也比 Dart isolate + 手挑 `Future` 省事。 | 平手偏 **Kotlin** |
| **体积与资源占用**（用户明确要求「不能太大」） | 5。装完 ≈30–50MB，安装包 ≈20–30MB，内存 ≈120MB。这是 Flutter 唯一压倒性赢的维度。 | 2。jlink 裁剪后 JRE ≈45–70MB + skiko 原生库 ≈40MB + jar ≈20MB → **装完 ≈120–160MB，安装包 ≈80–110MB**，冷启动 1.5–2s。已用 `modules = arrayListOf(...)` 只保留 10 个模块来止血。 | **Flutter** |
| **长期维护与生态** | 4。框架本身活跃，但 **desktop 是 Flutter 最不受重视的三等平台**：桌面专属插件稀少、bug 修复优先级低、没有第一方 WebView。 | 4。JetBrains 商业背书，Compose Desktop 已 1.x 稳定多年，JVM 生态里 B 站/WBI/二维码/HTTP/凭据存储全有成熟库；本项目用到的东西全部走 Maven Central。 | 平手 |
| **后续跨平台**（macOS/Linux/移动端） | 5。同一套 Dart 代码直接覆盖三平台 + iOS/Android，是 Flutter 的看家本事。 | 4。Compose MP 现在也支持 macOS/Linux/iOS（`1.12.2`），但**Android 侧不能直接复用这套桌面代码**（用户手机端管线还是 Kotlin/Android + Miuix，那边本来就是原生）。 | Flutter |

### 计分

Flutter 赢 2 项（开发效率、跨平台），且大幅赢体积；Kotlin 赢 4 项（桌面成熟度、进程集成、Python 协同、体积之外的维护），平 1 项。

## 三、为什么不看体积那一票

体积是 Flutter 最大的优势，也是本项目唯一认真权衡过的代价。理由：

1. **体积大头本来就不在 UI 框架。**需求书第三章要求的「虚拟 Linux 小环境」目标是 <1GB。真开这个环境（Debian/Alpine WSL 发行版）就是 200MB–1.4GB 量级，UI 框架省下的 100MB 在这个数量级前面不是决定性的；不开这个环境（本项目的默认形态，见架构文档第九章）则两边都是「纯 GUI + HTTP」，Kotlin 的 120MB 换 40MB 买不回失去的打包/进程能力。
2. **安装包是本项目唯一的硬交付物**（需求书第八章第 6 条「打包好的 exe 应用放到桌面」）。Kotlin 这条路径今天在本机就能产出 `.msi`；Flutter 得先解决 VS Build Tools 的安装。选一个「今天要交付」的方案。
3. **Agent 的核心工作是调外部世界**——起进程、读 stdout、管 cookie、加解密、限速、轮询登录态。这是 JVM 的主场，不是 Flutter 的。Flutter 在这里每一条都要开一条 platform channel 到 C++/WinRT，代码量和出错率都翻几倍。

## 四、被排除的第三、第四方案（免得回头再问）

- **Tauri（Rust + WebView2）**：体积最香（安装包 ≈10MB），UI 能直接吃到用户熟的 Web 组件库。**但本机 Rust 只有 GNU 工具链、没有 MSVC `link.exe`**，Tauri v2 在 Windows 上基本按 MSVC 假设构建（`webview2-com`、`windows` crate 的 GNU 链接支持残缺），且 `embed-webview` 需要额外 VC 运行库。要走通同一条「先装 VS」的路，而且装完仍然是未知数。**结论：等哪天机器上有 VS Build Tools 了再考虑，本项目不等。**
- **Electron**：安装包 ≈80–100MB、装完 ≈250MB、内存 300MB+，正面撞「体积优先」。且它同样没有内置 Linux 沙箱能力。**结论：否。**
- **Python + PySide6/Tkinter**：能直接复用现有管线，但 PyInstaller 打出来的单文件包解压慢、杀软误报率高，pip 依赖在目标机器上不可控，且和「把 Python 依赖干掉」的目标相反。**结论：否。**
- **JavaFX**：和 Compose 同为 JVM，但 UI 表达力和组件现代程度明显不如 Compose MP，且要额外捆 JavaFX SDK。**结论：否。**

## 六、遗留代价（明说，不藏）

1. 安装包 ≈100MB、装完 ≈150MB、冷启动 1.5–2s —— 这是 JVM 的税，已用模块裁剪压到下限。
2. UI 迭代循环比 Flutter 慢；改一次视觉要等 Gradle 增量编译。
3. 若将来真要覆盖 iOS/Android，Compose 桌面代码搬不过去，那时需要 Flutter 或 Compose MP 移动端重写 —— 但需求书第一章写明手机端管线保持原样不动，这条暂时不买账。
